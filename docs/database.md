# Database setup and foundation

## Local isolated cluster

`npm run db:local` uses installed PostgreSQL binaries to initialize `.local/postgres`, bind it to 127.0.0.1:55432, use SCRAM password authentication, and create `viotechpm` plus `viotechpm_test`. It generates an ignored `server/.env` using exclusive creation and refuses to overwrite existing configuration. A stopped cluster can be resumed with `npm run db:local:start`. The existing PostgreSQL Windows service on port 5432 is untouched.

`PG_BIN` can specify another installed PostgreSQL binary directory. The generated local database owner is for development only. For production, use a separate migration owner and a limited runtime user with the required table/sequence permissions. Keep `.local` private to your machine.

## Use your own PostgreSQL

1. Create a development database and a separate test database ending in `_test`, owned by your intended local role.
2. Copy `server/.env.example` to `server/.env` only if no configuration already exists.
3. Set `DATABASE_URL`, `TEST_DATABASE_URL`, `CLIENT_ORIGIN`, a random `SESSION_SECRET`, and bootstrap name/email/password. Percent-encode reserved characters in connection-string passwords.
4. Run `npm run db:generate`, `npm run db:migrate`, and `npm run db:seed` from the repository root.

Example SQL, run through your authenticated PostgreSQL admin connection (choose your own password; do not save it in source):

```sql
CREATE ROLE viotechpm LOGIN PASSWORD '<unique-local-password>';
CREATE DATABASE viotechpm OWNER viotechpm;
CREATE DATABASE viotechpm_test OWNER viotechpm;
```

The seed requires a bootstrap password of 14–128 characters. Repeating it does not change an existing account. Super Admins can create additional accounts through Team Members using the existing Argon2id password hashing. Credential reset remains outside the current scope.

## Tables

| Table                | Purpose and constraints                                                                                                                                                                  |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `roles`              | UUID primary key, unique role key/name, description, creation timestamp                                                                                                                  |
| `departments`        | UUID primary key, unique configurable name, creation/update timestamps                                                                                                                   |
| `users`              | UUID primary key, unique normalized email, Argon2id hash, required role FK, nullable department FK, active/inactive enum, profile image reference, creation/update/last-login timestamps |
| `audit_logs`         | UUID primary key, nullable actor FK, action, entity type/ID, timestamp, optional JSON metadata                                                                                           |
| `sessions`           | Session ID primary key, JSON payload, expiry timestamp; compatible with connect-pg-simple                                                                                                |
| `_prisma_migrations` | Prisma-managed migration history                                                                                                                                                         |

The initial migration is `20261026000100_foundation`. Role deletion is restricted when users reference it. Department deletion clears its optional user references. Deleting an actor preserves audit history and clears the actor reference. User role, department, status, audit actor/time, entity references, timestamp, and session expiry are indexed.

Session user IDs are inside the JSON payload, rather than a separate FK, to preserve compatibility with the PostgreSQL session-store adapter. Every protected request resolves that ID through `users`; deleted/inactive users cannot continue using their old sessions. Expired sessions are rejected and pruned. UUIDs and `updatedAt` are generated by Prisma on application writes.

Bootstrap inserts five roles and four departments: Software Development, IT Support, Infrastructure & Networking, and Administration. These are normal database rows. The first admin belongs to Administration. Bootstrap adds an audit event only when creating the user.

### Additive Phase 2 migrations

| Migration                   | Tables / changes                                                                                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `20261026000200_clients`    | `clients`, client type enum, unique uppercase codes, status/archive/creator indexes                                                                           |
| `20261028000100_projects`   | `projects`, `project_categories`, priority/project-status enums; decimal budgets; date/completion checks; eight configurable service categories               |
| `20261029000100_team_tasks` | `project_members`, `tasks`, task-status enum; unique project/user membership; manager-membership backfill; task date/completion checks and assignment indexes |

All three were deployed with `migrate deploy` to the existing application database and separate test database. No reset, drop, replacement users, or credential changes are required. Core relationships use restrictive foreign keys; soft archive preserves associations. User/Role/Department/AuditLog/Session tables are reused. Phase 2 adds no expense or approval tables. See [API rules](PHASE2_API.md) for completion, assignment, and account safeguards.

## Migration workflow

```powershell
npm run db:generate
npm run db:migrate
npm run db:seed
```

For schema development later, use `npm run db:migrate:dev -w server -- --name descriptive_name`, review its SQL, and commit the new migration. Do not edit already applied migrations. `migrate deploy` applies committed migrations without a shadow database or destructive reset.

## Future Neon configuration

No Neon project or production deployment has been created. When production is authorized:

1. Create the Neon database and select an appropriate region. Provision a limited runtime role and a migration owner.
2. Set the backend `DATABASE_URL` to Neon’s PostgreSQL runtime connection string with TLS enabled. Prisma uses its node-postgres adapter; the session store uses node-postgres directly.
3. Set optional `DIRECT_DATABASE_URL` to the direct migration-owner connection string for CLI migrations. If absent, Prisma CLI uses `DATABASE_URL`.
4. Keep certificate verification enabled. Use a verified CA chain; never use `rejectUnauthorized: false`. For pg connection strings, use the provider’s recommended certificate-verifying settings (for example `sslmode=verify-full`) and validate them in the target host.
5. Run committed migrations as a release step, then seed the first real admin using secret environment variables. Rotate/delete bootstrap secrets from the deployment environment after use.
6. Configure backend HTTPS, production cookies, trusted proxy, allowed frontend origin, and SPA rewrites on Vercel. Use a same-site frontend/API or reverse proxy. Keep database credentials only on the server.

Use a separate Neon branch/database for tests. The test runner refuses `TEST_DATABASE_URL` unless its database name ends in `_test` and differs from the application URL.
